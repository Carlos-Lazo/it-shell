La Fase 6 se implementa en `feat/phase-6-mcp-server`, basada en `main`. Se dividió en entregas pequeñas para validar cada capa antes de exponerla.

### 1. Definir contratos para las herramientas

Crear tres operaciones MCP, con argumentos y respuestas estructurados:

- **`search_commands`**: recibe una consulta y un límite; devuelve candidatos recuperados con alias, intención, comando, ejemplo y score.
- **`plan_operation`**: recibe una consulta y devuelve el análisis, los pasos, sus dependencias, la propuesta y las advertencias.
- **`validate_command`**: recibe un comando como texto y devuelve su nivel de riesgo, hallazgos y recomendaciones.

Ninguna herramienta ejecutaría comandos. Para `validate_command`, el comando sería solo texto que se pasa al validador.

### 2. Separar la lógica del motor del formato de la CLI

Ahora el motor termina formateando su respuesta como texto. Para MCP conviene exponer también un método interno que devuelva el `SearchResponse` tipado, y dejar que la CLI y el servidor lo serialicen cada uno a su formato. Así evitamos que el servidor tenga que interpretar JSON o Markdown generado para humanos.

### 3. Implementar el servidor MCP

Agregar `semantic_search_engine/mcp/` con un servidor basado en el SDK oficial de MCP para Python y transporte **stdio**. El servidor adaptaría las herramientas a los servicios existentes de retrieval, pipeline y validación. Configuraría la creación del motor en un único punto compartido con la CLI.

### 4. Validar entradas y errores

Definir límites razonables para longitud de consulta y `top_k`, validar argumentos y devolver errores estructurados cuando haya datos inválidos o no estén disponibles corpus/índices. Los errores no deben convertirse en resultados vacíos que parezcan exitosos.

### 5. Probar primero en memoria y luego con un cliente MCP

Añadir pruebas para cada herramienta: formato de entrada/salida, consulta sin resultados, entradas inválidas y detección de riesgos. Después, probar el protocolo con un cliente MCP de prueba que invoque las tres operaciones, sin requerir un cliente externo durante la suite normal.

### 6. Documentar integración y medir latencia

Crear `docs/mcp_integration_guide.md` con instalación, comando para iniciar el servidor por stdio y un ejemplo de configuración de cliente. Medir por separado arranque frío y consultas con el modelo ya cargado; el criterio de **menos de 400 ms** debería aplicarse a latencia en caliente y definirse con el mismo conjunto de datos y entorno, porque la carga inicial de embeddings puede superarlo.

**Orden propuesto:** contratos y respuesta tipada → `search_commands` → `plan_operation` → `validate_command` → pruebas de cliente → guía de integración y mediciones. Después de cada etapa correríamos sus pruebas; al completar la fase, la suite completa y una prueba integrada con el cliente MCP.
